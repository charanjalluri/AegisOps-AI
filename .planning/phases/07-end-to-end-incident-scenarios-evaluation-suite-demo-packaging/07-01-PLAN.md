# Plan 07-01: Declarative Incident Scenario Engine & Flagship Scenario

## 1. Objective
Build the declarative incident scenario engine that loads YAML failure specifications, injects operational faults into the microservice simulator and telemetry streams, triggers deterministic anomaly detection, and verifies scenario execution against ground-truth contracts.

---

## 2. Context & Requirements
- **DEMO-02**: Declarative incident scenario runner executing `demo/scenarios/database-connection-leak.yaml` (v2.8.1 deployment triggering pool exhaustion and 500 spikes).
- **DEMO-01**: Enhanced payment-service simulator supporting dynamic failure injection endpoints and simulated failure trajectories.
- **Threat Mitigations**:
  - `T-07-01`: Enforce strict `yaml.safe_load()` and Pydantic validation on all scenario files.
  - `T-07-02`: Guarantee standalone in-memory execution fallback when live Docker infrastructure is offline.

---

## 3. Tasks

### Task 1: Scenario Schema & Data Models (`apps/demo/models.py`)
- Define strongly-typed Pydantic schemas:
  - `FailureInjection`: target service, action (`deploy_version`, `inject_latency`, `exhaust_pool`, `simulate_error`), version, error rate, connection leak rate, and synthetic log messages.
  - `GroundTruthContract`: failure category, expected root cause keywords, expected MCP tools, forbidden tools, remediation action proposal, and verification metric conditions.
  - `ScenarioDefinition`: unique ID, title, description, service, severity, injection spec, and ground-truth contract.
- Implement validation helper `ScenarioDefinition.from_yaml(path: str)`.

### Task 2: Flagship Scenario YAML (`demo/scenarios/database-connection-leak.yaml`)
- Define the flagship database connection leak scenario:
  - Service: `payment-service`
  - Version: `v2.8.1` (commit `c4a1b2c`)
  - Symptoms: 50/50 connection pool saturation, 28.4% error rate spike, p95 latency 1850ms, timeout logs.
  - Expected Root Cause: connection pool exhaustion caused by unclosed connections in v2.8.1 release.
  - Expected Investigation Tools: `get_error_rate`, `get_connection_pool`, `get_deployment_history`, `get_recent_commits`.
  - Remediation: `rollback_deployment` to `v2.8.0` (`HIGH` risk).
  - Verification: `error_rate < 0.01`, `active_connections < 15.0`.

### Task 3: Failure Injection & Scenario Runner (`apps/demo/scenario_runner.py`)
- Implement `ScenarioRunner`:
  - `load_scenario(path_or_id)`: Loads and validates scenario definition.
  - `inject_failure(scenario)`:
    - If live HTTP simulator is reachable: POSTs to `/simulate/fault` or directly bumps version and simulates traffic.
    - If running standalone/offline: emits synthetic `RawLogEvent`, `RawMetricEvent`, and deployment events to Kafka or an in-memory event bus.
  - `trigger_investigation(scenario, graph)`: Dispatches the scenario incident to the LangGraph `InvestigationGraph`.
  - `verify_execution(scenario, state)`: Evaluates whether the investigation converged and whether synthesized RCA matches ground-truth keywords.

### Task 4: Microservice Simulator Failure Injection (`apps/payment_service/main.py`)
- Add failure injection endpoints:
  - `POST /simulate/version`: Swaps active version (`v2.8.1` vs `v2.8.0`).
  - `POST /simulate/leak`: Increases simulated active database connections.
  - `POST /simulate/reset`: Resets simulator to nominal `v2.8.0` baseline.

### Task 5: Unit Tests (`tests/unit/test_scenario_runner.py`)
- Verify:
  - YAML scenario parsing and Pydantic validation (rejects invalid fields / malicious types).
  - Failure injection lifecycle and telemetry event generation.
  - Standalone offline execution producing predictable incident trigger signals.
